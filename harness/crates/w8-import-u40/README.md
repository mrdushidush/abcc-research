# `w8-import-u40` — the 40-task Ollama stress battery, imported

The third importer, and the smallest. It exists to close one **§16 acceptance criterion** honestly
rather than by argument: the brief names ABCC's 40-task corpus, the set had never been imported
(`corpus/suites/` held `k`, `q56` and `u100`), and `prestudy/data-assets.md:23` marks it
*"Saturated"*. David's ruling, 2026-08-26: **import it and run it once.**

```bash
cargo run -p w8-import-u40 -- --out ../corpus          # emits corpus/suites/u40/
cargo run -p w8-corpus     -- ../corpus                # must print ACCEPTED
cargo run --release -p w8-run --bin w8-run -- ../corpus \
  --subject claudette-af3f804 --model 'qwen3.6-35b-a3b-mtp@iq3_s' --suite u40 \
  --bin D:/dev/claudette/target/release/claudette.exe --out ../runs/u40-r1
```

⚠ **Pass `--bin`.** Without it the runner resolves `claudette` from `PATH`, which on this host is an
older install; the block probe catches it and refuses the whole run, which is the harness working
as designed (`w8-run/README.md`, "the block probe and the silent failure it exists for").

## Why a third crate and not a flag on `w8-import`

`w8-import --donor` takes the repo *directory* and `donor.rs` is hard-wired to
`scripts/ultimate-100-task-test.js`, with a byte-walker built for that file's multi-line template
literals and its `BUGGY_FILES` map. This donor has neither: **one flat `const TASKS = [ … ]` of 40
object literals with five keys each**. Bending the 100-task walker around a strictly simpler file
would make both harder to read for no gain. `w8-import-q56` set the precedent.

Kept from the other two, unchanged: it **never drops a task** (a `broken` gate point means
`quarantine = "with_baseline"`, not exclusion); it **never overwrites an authored file** (generated
files carry `GENERATED by w8-import-u40` in their header and `--force` refuses anything without it);
and it **reads the donor through `git show`**, so the donor cannot even be a working tree.

## What this import found before it emitted anything

Four things, each of which changes how the resulting number may be quoted. All four are recorded in
`corpus/suites/u40/suite.toml`'s caveats, where a reader of the corpus will actually meet them.

1. 🚨 **The recorded 39/40 is an after-retry number.** It was written by commit `01246c1`, whose
   own message is *"auto-retry pipeline — 90% → 98% pass rate (39/40)"* and which describes phase 0
   validate → phase 1 Ollama retry with the error in context → phase 2 **Haiku** escalation. The
   same 40 tasks scored **36/40 on one attempt, three times, on two configurations**, and 35/40 on
   a 7b. **The honest single-attempt floor is 36/40.**
2. 🚨 **The prompt the model saw was `description`, not the `fullDescription` that `createTask`
   builds** — which interpolates `task.code`, the reference solution, into the prompt text.
   `fullDescription` is posted to the task DB record; `executeTask(:412)` sends `task.description`,
   and the agents service uses `request.task_description` verbatim
   (`packages/agents/src/main.py:325`). The proof is independent of both call sites: **17 of 40
   tasks name a different file in the DB record than the prompt and the verifier agree on**
   (`c9_stack_class` vs `tasks.c9_stack`), so a run driven by `fullDescription` would have failed at
   least those 17 on the filename alone. It failed one.
3. 🚨 **One task has never passed, in any recorded configuration.** `flatten_list` (`c5_flatten`) is
   a failure in all five recorded runs, including the one with the retry pipeline and Haiku in front
   of it. This import is the first time its verifier has been run against a known-correct answer —
   gate point 2, which **passes**, so the task is solvable and the donor's stack never solved it.
4. **The tasks are byte-identical across the versions that matter.** The `TASKS` array is the same
   at `01246c1^` (before auto-retry), at `01246c1` (the 39/40 run) and at `d5528ea` (HEAD). The only
   later change to the file is `fed42d3`, which base64s the validation string on its way into
   `docker exec`. So the tasks imported here are the tasks that ran.

## What the emitted suite contains

40 tasks, `lang = "python"`, `kind = "function" | "class"`, `timeout_s = 300` (the donor's global
`TASK_TIMEOUT_MS`), one `[[turn]]` sending `prompt.txt`, and per task:

| file | provenance |
|---|---|
| `prompt.txt` | **verbatim** — the donor's `description`, and the reference solution nowhere near it |
| `verify.sh` | **rewritten** — four changes, none touching an assertion (below) |
| `fixture/tasks/__init__.py` | **rewritten** — the donor's own `touch /app/workspace/tasks/__init__.py` (`:362`), per task instead of once per campaign |
| `refsol/tasks/<id>.py` | **verbatim** — the donor's `code` field. The answer key, and the gate's point-2 input |

**The id is the artifact's stem, not `c{complexity}_{name}`.** The donor's own file-naming rule
disagrees with its prompts on 17 of 40; the prompt and the verifier always agree, so the artifact
path is the authority.

### The verifier rewrite, four changes

1. The `docker exec -w /app/workspace` execution model becomes the runner's work dir, with the work
   dir on `sys.path` — which is exactly what `-w` bought the donor, since every validation is a
   `from tasks.<mod> import …`.
2. The interpreter resolves through `$PYTHON` (SPEC §8), so the same task runs on host or container.
3. A missing interpreter prints `INVALID`, not `FAIL`. The donor's `catch { return false }` makes
   *"the verifier did not run"* and *"the artifact is wrong"* the same fact; SPEC §8 has a third
   verdict for exactly this.
4. **The donor's PASS contract is preserved rather than replaced.** It scores
   `result.includes('PASS')` over captured stdout — not "no exception" — so stdout is captured here
   too and a body that completes without printing `PASS` is a FAIL. All 40 validations end in
   `print('PASS')`, so the two rules agree today; keeping the donor's is what makes that agreement a
   fact rather than an assumption.

The assertion body is **executed, not inlined**, inside a raw triple-quoted literal, so reformatting
can never become an unrecorded edit. `donor::parse` refuses any validation that could not survive
that literal.

### The gate is stronger here than in either other suite

SPEC §9 has three points and this suite can answer **two**, where u100 could answer one:

- **point 1 — rejects a non-answer**: two pre-states, *absence* and a *null-implementation stub*
  (absence alone only proves the import machinery raised — F19). **Sound on 40 of 40.**
- **point 2 — accepts a correct answer**: the donor ships a reference solution, so this runs for
  real. **Sound on 40 of 40.** U100 had no refsol and recorded `not_run`.
- **point 3 — rejects a plausible wrong answer**: no sham exists for this donor, so `not_run` and
  `[selection]` is absent, which is how SPEC §9 says *"not in the sham set"*.

### One variant, deliberately

`control`, `permissions = { mode = "allow" }` — donor-faithful, since the recorded runs drove a
CrewAI agent whose `file_write` had no permission prompt in front of it. **This suite cannot measure
operator control**: all 40 tasks create a file that does not exist, and creating a new file never
fires a gate whichever edit tool the model reaches for (F39). That is the gap Q56 was sourced to
fill (F38, F40), and a `gated` variant here would pass by construction.

## Traps

- 🚨 **`code:` is the reference solution and it must never reach `prompt.txt`.** It reaches
  `refsol/` and the gate, and nothing else.
- 🚨 **Read `description`, not `fullDescription`.** See finding 2 above; the 17 disagreements are the
  test that catches getting this wrong.
- **The scanner must be string- and comment-aware.** `code` values contain `{`, `}` and `//` inside
  strings (`f'Hello, {name}!'`, `token in '+-*/'`), so a brace counter or a line regex silently
  mis-slices the array.
- **CRLF is normalised on read**, as `w8-import/src/donor.rs` does — the 100-task donor was entirely
  CRLF and it silently emptied two fixtures before anyone noticed.
- **`bash` on Windows PATH is the WSL launcher**, which fails with a WSL configuration error before
  it reads the script; `python3` is a Store alias shim that prints an advert and exits 9009. Both
  interpreters are probed **by executing**, never by looking up — the first version of the gate here
  scored 0/1 on both points for exactly this reason.
- **The count is the boundary.** 40, or the import emits nothing.
